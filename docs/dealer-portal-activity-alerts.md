# Dealer Portal activity alerts

- New all-member Dealer Network Board topics get one email per active, unlocked member in the published topic's recipient snapshot. The existing topic/poll bell still supplies a single notice; the new delivery queue does not create another topic bell. New comments and direct replies on those all-member topics also get one email and one bell each. An eligible author is included.
- Legacy and targeted topics keep their previous recipient access and existing topic/poll/discussion notices. They do not start new comment/reply fan-out. There is no historical audience flag that reliably distinguishes former full-network topics from targeted imports, so we do not infer audience from member counts or migrate any historical alerts. A new all-member topic never alerts someone outside its existing readable audience, including a member who joined after the topic's snapshot.
- A Troubleshooting issue alerts members when it is first approved and visible, not while it is pending or denied. New comments and dated author updates alert only while the issue is approved. Edits, removal, revision approval, and changes to public website publication do not create notifications. The migration records currently approved issues as previously approved without generating notices; earlier approvals of older issues no longer approved are not reconstructible from current status.
- Email carries only a generic label and a link back to the canonical Dealer Portal. It contains no title/body, photos, or other member information. The link preserves its exact Board topic or Troubleshooting entry/activity through sign-in; server access checks are still required. Private direct messages, drafts, scoped topics and private author notes are not included in the new alert stream. Existing direct-message behavior is untouched.
- Delivery uses one transactionally queued notification per event and member, and only the currently eligible recipient can be resolved server-side for sending. Portal bell notices do not depend on the email provider. Opening a visible message clears only the relevant recipient's alert.
- A Vercel production cron authenticated by the existing CRON_SECRET drains at most 25 notifications every two minutes. Leases and the stable per-delivery Resend idempotency key prevent overlap and retry duplicates. The attempt window is limited to five claims and 12 hours after the first claim, deliberately shorter than Resend's documented [24-hour deduplication window](https://resend.com/docs/dashboard/emails/idempotency-keys). Undeliverable mail does not roll back an already posted message; permanently failed delivery remains in the ledger for investigation rather than being blindly resent. Large bursts can take more than one batch.
- Release only if separately authorized. Apply the single additive migration before the app; confirm the new service-role-only RPCs are available through PostgREST, then deploy the exact build to production. Preview must not use production DB credentials or send mail. Use only a synthetic fixture and a local HTTP mail sink for delivery verification. Verify the live route returns 401 without authorization and provider logs are scoped; never add test content to the live portal or invoke the live worker just to test. The prior app can be restored (its original Board RPCs remain); leave the additive ledger, markers and data intact when rolling back the app.
